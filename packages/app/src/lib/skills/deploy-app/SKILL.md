# Deploy a TeamClu app

The checkout declares the desired build and start behavior. The live deployment and regional capabilities are separate facts. Resolve both before making a deployment decision.

Every step is an `amuxd app` command (`amuxd app <command> --help` shows its arguments). Each prints one line of JSON and exits with a status that says what happened: 0 done, 2 fix the arguments, 4 not allowed, 5 not found or ambiguous, 6 conflict (follow `next`), 7 platform error (see `retryable`), 8 outcome unknown.

1. Run `amuxd app status` in the selected app workspace. Read the current checkout declaration, live deployment, code revision, and source status. Treat the session snapshot as a hint only.
2. Run `amuxd app runtime --language <language>`. Use the returned regional versions, image observations, layer availability, verification status, and source errors. For a new app, select a TeamClu-deployable candidate from current facts and write every required startup field explicitly. Provider availability alone does not establish TeamClu compatibility. Do not guess a version, path, layer, or compatibility from a template or another region. If discovery times out or is incomplete, keep that uncertainty visible; it does not authorize silently switching to a familiar runtime. A routine redeploy may retain a verified, pinned live configuration when catalog discovery is unavailable and there is no provider drift.
3. Preserve the successful deployment's FC runtime, interpreter command and version, args, layers, and port for an ordinary redeploy. A runtime, interpreter, or layer change is a migration: explain the exact fields and reason, and pass `--migration` only with the user's explicit migration intent; the deploy's preflight states the exact changes. Entry and port changes must also be visible in that preflight. Never rewrite the checkout to a known-good version merely because discovery failed.
4. Check the **selected build machine** and its tools. The build command runs there, possibly on Windows, while the function runs on `linux/x86_64`. Verify the declared output and entry exist, and that native dependencies target Linux/x86_64. The daemon's build response includes `artifactVerification` for the pinned `revision`: `checked` means the declared entry and recognizable native headers or local image metadata passed those checks; it does not prove the app starts. ZIP/JAR members are checked through EOF within fixed limits; nested, oversized, corrupt, or unreadable archives stay unknown. Tar and other compressed formats that the daemon cannot inspect also stay unknown. A wrong platform fails before archive upload or image push. `unknown` blocks automatic finalization; it names an opaque startup entry, unclassifiable native content, or unavailable image metadata. The previous version stays live. Run an explicit test in the target Linux/x86_64 runtime before treating it as compatible. The current deploy path has no evidence override, so report the deployment as blocked rather than retrying or claiming it published. Keep build commands portable across selected machines.

   For FC container images, do not attach build provenance attestations. Use `docker buildx build --platform linux/amd64 --provenance=false` when specifying a container build command; the daemon's default container build uses these flags. Buildx provenance can add an `unknown/unknown` entry to the OCI index, which FC may reject as an incompatible image. Check the pushed image manifest when diagnosing this failure.
5. For a Gitea checkout, commit and push the exact app revision to its remote, then verify the **selected checkout is clean and at the exact remote HEAD**. A clean remote commit does not excuse a dirty selected checkout, even if the build would read remote content. Gitea deployment cannot use uncommitted or unpushed changes. For an imported checkout, use the platform's pinned content digest and its source checks.
6. Only when the user explicitly requested publishing, run `amuxd app deploy`. amuxd runs the deploy and the command waits for it; if your command is cut off, the deploy keeps going — run `amuxd app op wait <op>` with the `op` it printed, never a second deploy. Exit 8 means the outcome is unknown: read `amuxd app status` before doing anything else. Do not work around a refused preflight or drift. Deploy the pinned revision, then check `amuxd app status`, the runtime configuration, live URL, health path, and changed behavior, including data/auth behavior when applicable. Report the revision and any verification limit.

Environment, access, login wall, domain, data, files, and cron changes use `amuxd app env|access|gate|domain|data|files|cron`. Every command acts as this daemon's agent account and the platform decides what it may do: exit 4 means that account lacks the grant — tell the user who has to grant what level, do not look for another way. Never request or print secret values; a secret goes in through stdin (`amuxd app env set KEY --secret`), never on the command line.

For TeamClu platform sign-in, organization roles, or protected pages and data endpoints, read the inherent `app-auth` skill before implementation. At release, verify its saved policies and report any auth acceptance limits.

## Database changes (`migrations/`)

Nobody can open a data app's database directly: not you, not the user, not another agent. Its credentials exist only inside the deployed function. So never hand the user a script to "run against production", and never block a deploy waiting for someone to create a table. Put every schema change in the checkout's `migrations/` folder and deploy:

- One plain SQL file per change, named `NNNN_description.sql` (e.g. `0001_create_scan_tasks.sql`). Files run in name order, each once, each in its own transaction, as the app's own database role, with unqualified names landing in the app's schema. The platform records them in `_teamclu_migrations`. Every `.sql` file in the folder must follow this naming, or the build stops.
- They run at deploy finalize, before the new code goes live. A failing file is rolled back and stops the deploy, and the previous version keeps serving. Read the error, fix that file, and deploy again.
- Never edit or rename a file that has been deployed. The deploy refuses a changed one (`migration_modified`), so put a correction in a new, later-numbered file. A new file must sort after every applied one (`migration_out_of_order`).
- The old version keeps running against the new schema until the new function takes over, so every migration must be **additive**: new tables, nullable or defaulted columns, new indexes. Drop or rename in two deploys: first stop using the old column, then remove it in a later migration.
- No `BEGIN`/`COMMIT`/`ROLLBACK`/`SAVEPOINT` and no `CREATE INDEX CONCURRENTLY` (the file already runs inside a transaction). A file wrapped whole in one `BEGIN; … COMMIT;` is accepted and the wrapper ignored; any other transaction control stops the deploy before any file runs. Each statement times out after 120 s, a lock wait after 15 s, and a file's whole transaction after 5 minutes (`migration_stalled`).
- Only data apps (`type: data_app`) have a database. A `migrations/` folder on any other type stops the deploy (`app_has_no_database`).

## Uninstalling a deployment

Only when the user explicitly requests uninstalling a deployment, run `amuxd app undeploy` with an explicit app ID or name (`--id` / `--app`); it does not act on the app inferred from the current directory. This stops new gateway requests and cleans the FC function, HTTP trigger, origin domain mapping, build artifact and any legacy login client. It retains the App, code repository, sessions, database, uploaded files, auth policy and scheduled-job definitions. It does not delete the App or archive its repository.

`undeploy` waits for the uninstall itself (up to 5 minutes) and answers with its outcome: `complete: true` means it is done; a failure is an `undeploy_failed` error naming the failed steps — report them and retry only when the user requests it. Only if the reply says `complete: false` (still running after the wait) read `amuxd app status` until `undeploy_operation.status` is `succeeded`. An unknown provider outcome remains fenced for operator reconciliation: do not force a new deploy or bypass the lock. After successful uninstall, use the normal deployment flow to publish again, retaining the last successful configuration as history. Verify retained data and platform login after redeployment; report real-account verification as pending when unavailable.
