# App 卸载部署设计规格

日期：2026-10-05
状态：待用户审阅
范围：TeamClu 平台、Web/桌面和 Agent 工具；不修改用户应用业务代码。

## 1. 目的与已确认范围

用户需要卸载 App 的线上部署，而不是删除 App。卸载后线上地址停止提供应用服务，清理该 App 的运行资源及部署产物；App、代码仓库、会话、数据库和上传文件保持完整，之后可以通过正常部署流程重新上线。

操作需要 App 管理员权限和明确确认。创建者是否有管理员权限继续使用现有平台权限解析，不新增创建者 ID 白名单。

成功标准：线上请求不能到达旧应用；平台能准确报告清理成功或失败；保留的数据可在重新部署后继续使用。

## 2. 方案选择及现状

选择独立的卸载生命周期和 API。与删除 App 共用可分离的底层资源删除适配器，但不调用完整的删除流程。

现有 `teardownAppResources` 会删除函数、构建产物、禁用 OAuth 客户端，并归档仓库；它按 best-effort 吞掉异常。现有 `deleteApp` 还会归档工作区及会话并删除 App 行。这些语义不能直接用于卸载。

另两个方案不采用：仅阻断网关访问仍留下运行资源和费用，不满足清理要求；复用删除 App 会损害代码和会话的可恢复性。

## 3. 资源边界

| 资源 | 卸载行为 |
| --- | --- |
| App 行、工作区及会话 | 保留，不归档 |
| Gitea 仓库及代码访问凭据 | 保留，不归档、不撤销开发访问 |
| 数据库/schema、数据、业务 secrets | 保留 |
| 上传文件 `app-files/<appId>/` | 保留；禁止按 App 前缀泛化清扫 |
| 构建产物 `apps/<appId>/code.zip` | 删除，仅限该对象 |
| FC 函数及所属 HTTP Trigger | 删除，仅限记录/推导确认属于此 App 的资源 |
| FC 源站自定义域名映射 | 清理该 App 映射；不删除共享入口或其他 App 资源 |
| 用户配置的公网域名、DNS 验证及权限规则 | 保留配置；停止转发到应用，不删除用户 DNS |
| 平台登录 OAuth 客户端 | 禁用，不删除业务数据；重新部署恢复或重新创建有效客户端 |
| 定时任务定义及历史 | 保留；离线时停止调度，不补跑卸载期间错过的任务 |

重新部署前必须检查禁用的 OAuth 客户端和相关 secret 能否恢复使用；若重新创建，原子更新引用和凭据。不能保留一个禁用客户端却宣称登录已恢复。

## 4. 生命周期与并发

引入持久的卸载操作状态，不能只靠桌面内存或 HTTP 请求存活：操作 ID、开始时间、执行租约、每项资源结果和可脱敏的错误。

对外状态至少区分 `uninstalling`（卸载中）、`uninstall_failed`（已停止访问，清理未完成）、`uninstalled`（已卸载）。未部署过的 App 保持现有未部署语义。

运行状态与历史信息分开：保留最后成功部署的 revision、runtime、启动声明及部署历史作为下一次部署参考，但它们不代表当前在线。卸载不清空权限配置或部署声明。

开始卸载时以数据库条件更新抢占该 App 的生命周期操作，同时撤销未消费的部署预检令牌。构建、上传、发布中拒绝卸载并返回 409；卸载中或清理失败未完成时拒绝新的部署和预检。删除 App 与卸载也必须互斥。

部署 finalize 必须重新验证当前操作状态/令牌，过期请求不能把已卸载状态改回在线。外部资源创建与清理使用同一 App 生命周期互斥约束；仅阻止最终状态写回不足以防止泄漏或误删。

完成卸载后允许正常预检和重新部署，重新创建运行资源；历史部署配置继续作为已知配置参考，不伪装成活跃 FC 读回。

## 5. 执行顺序与失败恢复

1. 校验管理员权限并原子登记卸载操作。
2. 持久标记应用不可转发；失效所有公网域名/网关缓存。缓存命中也必须在转发前确认可服务状态，不能仅依赖缓存 TTL。定时任务停止发起新请求。
3. 等待或终止已有平台生命周期操作的互斥窗口；不要求撤回已发送的业务请求，正在执行的请求可能完成。
4. 分项清理 Trigger、源站域名映射、函数、构建产物和禁用登录客户端。各项独立记录结果，一项失败仍尝试其余项。
5. 全部完成才标记已卸载；任一失败标记清理失败，保持网关关闭。

只将供应商明确的资源不存在视为幂等成功；权限不足、超时和网络错误不得视为已清理。错误不包含签名 URL、token 或 secret。

持久操作由可恢复的执行器处理，客户端断开不丢失任务。执行租约过期后可恢复，手动重试使用同一目标资源快照，只执行未完成项；重复提交不产生另一组并行删除任务。

此处的停止访问表示新请求不再转发。不得承诺请求撤销，也不得在清理失败时宣称函数已停止计费。

## 6. Cloud API 与 Agent 契约

先在 OpenAPI 定义 `POST /v1/apps/:appId/undeploy`，异步接受返回 202，响应含 App 状态和操作 ID。已卸载时幂等返回当前成功结果；已在卸载时返回已有操作。清理失败时允许该端点启动串行重试。

`GET /v1/apps/:appId` 暴露卸载状态和脱敏的分项结果，供 UI、Agent 及重试恢复读取。不新增客户端直连 Supabase。

无权限不得产生任何外部删除副作用。不存在/不可见的 App 延续现有 404 策略；生命周期冲突返回 409 并解释阻塞状态。

增加 `manage_app action: undeploy`，复用当前 App 选择/实例绑定与原生审批机制。确认内容列出 App 名称、线上地址、会清理的资源和保留的数据。Full Access 不绕过本操作的专用确认。

工具回复区分已接受、已完成及部分清理失败；不能以 202 当作卸载成功。`status` 能查询操作进度。`deploy-app` skill 使用英文补充卸载、重试及重新部署契约；AGENTS.md 不扩展详细部署说明。

## 7. Web/桌面体验

App 设置增加“卸载部署”，与“删除 App”分开。仅有管理权限且存在部署或待清理资源时展示可执行操作；未部署时禁用。卸载失败提供“重试清理”。

确认框明确：“线上应用将停止服务。代码、会话、数据库和上传文件会保留，之后可重新部署。”操作成功后显示“已卸载”，不继续显示 Live 或可访问的在线预览。

卸载中显示进度并禁用冲突操作；失败显示哪些资源尚未清理及重试入口。其他窗口重新读取权威 App 状态，不引入新的跨窗口持久状态同步机制。

公网离线响应统一使用 503 的非缓存页面/JSON，文案“应用尚未上线或已下线”，不泄露资源、数据库或内部错误。平台保留域名配置以便重新上线；自定义域名仍可能保留 DNS 和入口证书。

## 8. 回归与验收

- 权限：管理员可卸载，非管理员、不可见 App 和错误实例不能卸载；被拒绝时无外部副作用。
- 数据保护：不归档仓库、工作区或会话；不删除 schema、业务 secrets、上传文件、任务历史和权限规则。
- 清理：覆盖函数、Trigger、源站映射、产物及 OAuth 禁用；不存在幂等成功；供应商拒绝/超时正确报错。
- 恢复：每项失败、客户端断开、执行器中断、租约过期、重复请求和重试不丢任务，不误报成功。
- 并发：部署 start/finalize、预检令牌、删除 App 与卸载互斥；旧 finalize 不复活应用，不创建遗留资源。
- 入口：默认域名、自定义域名、缓存命中及定时任务均停止转发；不影响其他 App。
- UI/工具：确认文案及资源边界、进度、失败重试、已卸载幂等、非管理员入口、202 不当作完成。
- dev 新建专用测试 App：部署并写入数据/图片，卸载后验证网关离线及供应商资源清理，再部署验证数据/图片保留和平台登录恢复；覆盖一个清理失败后的重试。

线上验收仅针对专用测试 App，不卸载已有用户 App。真实登录验收需要可用账号和获授权的交互能力；无法登录时列为待验收，不能用 mock 代替真实登录通过。

## 9. 交付边界

本阶段只提交规格，不实施或部署。后续计划需要落实持久操作存储、生命周期互斥及执行器恢复机制的具体代码位置和迁移。

不新增自动过期卸载、批量卸载、数据库删除、仓库删除、iOS 界面或旧应用批量迁移。live schema 变更遵循仓库 Supabase MCP 约束；未具备 MCP 时不擅自应用迁移。
