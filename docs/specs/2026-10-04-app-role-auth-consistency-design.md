# 应用角色鉴权：平台工具与权限界面一致性修复规格

状态：待用户评审。仅批准了编写规格，尚未批准实现计划或代码实施。
日期：2026-10-04

## 1. 目标与范围

让 TeamClu 桌面权限界面、Agent 控制面工具及应用登录网关使用一致的组织角色规则。Agent 能查询真实角色目录，正确配置并读回权限；用户打开、保存旧规则时，访问范围不会因界面转换而悄然改变。

本次只修复平台。不得修改 james-test-app7 或其他测试应用的代码、环境变量、员工接口路径和线上权限；不得代替 TeamClu Agent 修复应用。

不重构现有组织与团队成员模型，不新增角色、不调整角色分配，不把组织角色改成 team 独立角色。不增加创建者 ID 白名单，也不新增基于 User ID 的员工权限模型。

## 2. 已确认事实

- app7 的控制面原始规则是 `[{"path":"/staff","auth":"required","audience":"org"}]`，`authScope=paths`。
- 桌面 `ruleToRowState` 将旧的 `audience: org` 转换为当前全部有效角色 codes。该组织当前目录为 owner、admin、member、finance，故界面显示四个勾选。
- `buildAuthPolicyPatch` 将上述 UI 状态写成固定的 `roles` 数组。这会把“任意有效组织角色”改成“当前这些指定角色”，对未来新增角色的行为不同。
- Agent 的 `manage_app` 工具 schema 描述 audience，却未描述规则中的 roles。桌面更新处理原样转发 authRules，并未把 roles 改成 audience。
- Cloud API 已提供组织角色目录；API 路径含 teamId，但目录及分配的实际范围是该 team 所属组织。现有 Settings「Team Roles」说明也是 org-scoped。
- 网关按应用所属组织查询当前有效角色，并判断与规则的交集。
- app7 另有依赖未配置 `STAFF_CREATOR_USER_ID` 的应用内检查。这是独立的应用问题，本次不处理。

尚未获得 app7 首次写入规则的完整工具调用记录。因此不把“某次 Agent 调用写入旧格式”当作已证实的历史事件；工具契约落后和读写语义变化已有直接证据。

## 3. 权限语义契约

### 3.1 三种登录受众

继续使用现有存储与 HTTP 契约，不新增数据库字段。UI 内部使用可区分的受众状态，不能仅用 roleCodes 数组表示全部情况。

| UI/工具语义 | 每条 required 规则的规范写法 | 行为 |
| --- | --- | --- |
| 任意已登录用户 | `roles: []` | 不要求组织角色 |
| 组织内任意有效角色 | `audience: "org"`，不写 roles | 动态判断该应用所属组织内任意有效角色，包括未来新增角色 |
| 指定组织角色之一 | `roles: ["role_code", ...]`，非空 | 必须命中一个明确选择的有效角色 |

公开规则写成 `{path, auth:"public"}`，不携带受众条件。角色列表表示 OR，不要求同时拥有全部角色。不硬编码 owner/admin/member/finance；真实目录可含其他有效角色。

保留现有 precedence：显式 roles（包括空数组）优先于每条规则的 audience，再优先于应用 authAudience。读取旧规则时必须遵循此顺序。若已有规则同时带 roles 和 audience，不据 audience 覆盖 roles；用户没有改变受众时保留原始规则，不进行无提示清理。

### 3.2 旧规则无损读取与保存

- 显式 audience: org 显示为“组织内任意有效角色”，不勾选当前全部角色。
- 旧 audience: any 显示为“任意已登录用户”。未编辑的规则保留原始表示；用户明确更改受众时可使用规范写法。
- 未声明 audience/roles 的旧 required 规则显示“继承应用默认：……”并展示解析结果。未编辑时保留字段缺省，不能擅自改成独立固定规则。
- 旧 `authScope=all` 且无 `/` 规则时，基准行代表应用级 authAudience。无改动不得生成新的固定角色 `/` 规则。
- 编辑一个路径，不改写其他路径的受众。规则顺序或角色数组排序不能掩盖语义变化。
- 打开页面不写权限。纯加载不标记 dirty；没有改动时保存按钮禁用。
- 用户主动在三种受众之间切换时清楚显示变化，特别是从动态任意角色改为固定角色时，不自动选满目录。
- 全量替换 authRules 的既有 API 保持不变；前端及工具必须先读取并保留未修改规则。

### 3.3 身份与权限边界

User ID 标识访问者，Actor ID 标识成员/参与者记录；二者不能相互替代。App 创建者/协作者控制代码管理权限，不自动获得线上页面的角色访问权限。

组织角色是本次唯一使用的角色范围。它不是“必须属于应用的那个 team”：在当前模型下，同一组织不同 team 共享组织角色。仅移出某个 team 是否同时撤销组织角色，属于现有成员生命周期模型，不能在本次设计中假定两者等价。

## 4. Agent 控制面工具

### 4.1 新增只读 `manage_app auth_info`

使用与 status 相同的 app_id/app_name/当前 app 工作区选择方式，通过已认证 Cloud API 获取事实，不从模板、角色名常量或本地缓存猜测。

返回：

- app_id、team_id。
- 组织 ID、组织名称及明确的 `role_scope: "organization"`。
- 当前可配置的有效组织角色目录：id、code、name、status。
- 原始 auth_mode、auth_scope、auth_audience、auth_rules。
- 各规则的有效受众解析：public、any_authenticated、any_org_role、org_roles；标明是否继承及来源。
- 查询不可用时返回明确错误或 unavailable 状态，不以空目录代替失败。不返回用户清单、访问令牌、密钥。

权限：沿用应用读取权限和既有角色目录读取权限，不通过新 action 绕过 team/组织可见性。无权限时说明失败的资源，不静默扩大数据可见范围。不增加角色创建、分配、撤销功能。

status 保留原始规则，避免与 auth_info 矛盾。auth_info 不修改配置，不触发部署审批。

### 4.2 更新工具 schema 与说明

- auth_rules 的 items 声明 roles 字符串数组、三种受众的区别和匹配组织的范围。
- auth_audience 明确为应用默认/兼容回退，不再描述为唯一的 WHO 配置。
- 说明路径按前缀最长匹配；`/api/staff` 已覆盖子路径，不接收字面通配符 `*`。
- 配置前读 auth_info；使用真实 role code，不把名称或角色 ID 当 code，不自行创造角色。
- 更新前读已有规则，更新后读回原始规则及有效语义。工具和 UI 必须使用同一解析语义。
- 保留现有原生权限审批和 app admin 检查。不得绕过拒绝或未完成的审批。
- `manage_app_access` 继续只管理应用协作者，不与线上登录受众合并。现有管理 ROLE.md 的工具不是组织 RBAC 角色查询工具，说明中避免混淆。

### 4.3 Cloud API 契约

新增只读 `GET /v1/apps/{appId}/auth-info`，先在 OpenAPI 中定义资源及响应。FC facade 与 repository contract 聚合应用、所属组织元信息和已有角色目录读取，保留上述权限边界；桌面 introspect 不直接访问 Supabase。

不将组织目录全量复制到 app 行，不引入第二套角色存储。无法解析应用所属组织时标记未配置并停止角色配置，不退回其他组织。所需数据已有存储，不计划修改数据库 schema/RLS；若实现发现必须改变，须先更新规格和迁移/pgTAP 范围。

## 5. 桌面 UI

- 规则行明确区分三种受众；“组织内任意有效角色”与“选择指定角色”不能共用自动全选状态。
- 显示权限使用的组织名称。角色下拉仅在指定角色模式下使用真实目录。
- Settings 角色目录入口改为“组织角色 / Organization Roles”，说明同组织跨 team 共享，不暗示是 team 独立目录。
- 目录加载失败时展示错误，阻止依赖目录的角色修改，保留已有规则；不得清空选择或写出 roles: []。
- 已保存但现已失效/消失的角色明确显示，不静默移除。不能保存的原因由 API/界面报告，不能自动放宽规则。
- 展示与保存必须一致，保存失败保留草稿并报告错误，不能表现为成功。成功后使用服务端返回值刷新，再重新读取确认。
- 使用现有设计 tokens、i18n 和编辑布局；不扩展为组织管理新页面。

## 6. 网关行为与角色变化

沿用现有组织 RBAC 决策与身份头保护，不新增应用内白名单或角色授权来源。平台回归测试须证明：

- 受限请求基于当前有效组织角色，而非登录时的角色快照；角色撤销/失效后，旧登录会话的后续请求也拒绝。
- 动态任意组织角色规则会接受未来新增且有效的角色；固定 roles 规则不会自动包含它。
- 创建者没有匹配角色时没有自动绕过。
- 请求不得靠客户端伪造平台身份头获得身份，网关继续剥离客户端同名头。
- 错误、无法读取角色或损坏规则不能被解释为 roles: []。不降低现有拒绝行为。

本次不建立新的直连入口隔离机制；仅验证既有边界。若发现网关本身可被绕过，将作为独立平台缺陷报告、扩展规格后再处理。

## 7. 部署 skill 与提示范围

更新平台维护的 deploy-app skill，提醒 Agent：平台登录页面和实际数据接口需要分别核对路径规则；路径权限不覆盖未被规则匹配的接口。使用 auth_info 查询组织及角色，不为角色权限额外生成固定 User ID 白名单。

这属于应用开发/部署指导，不代表平台自动推测业务接口，也不强制使用 `/api/staff`。公共申请人和员工共用的 Server Functions 路径不能由平台擅自整体上锁。

session_prompt 保持通用，不加入详细部署或鉴权教程。既有应用不会因更新 skill 被自动改写或重新部署。

## 8. 验收与回归

| 场景 | 验收结果 |
| --- | --- |
| app7 当前 audience: org 读入 | 显示动态任意组织角色，不显示四个具体角色已勾选 |
| 打开旧规则且未编辑 | 无网络写入，保存禁用，原始配置不变 |
| 修改其他路径后保存 | 未修改的旧规则和继承语义保留 |
| 动态任意组织角色保存并读回 | 仍为动态条件，不固定到当前目录 |
| 指定角色由 UI 写入、工具读回 | role codes、组织范围及有效语义一致 |
| 指定角色由工具写入、UI 读回 | 显示相同选择，不丢 roles，不变成 audience |
| 无匹配角色/角色撤销/角色失效 | 受限请求拒绝，即使 cookie 尚有效 |
| 当前目录后新增角色 | 动态规则接受该有效角色；固定角色规则不接受 |
| 角色目录失败/越权/未知 role code | 明确失败，不扩大访问范围 |
| 角色目录包含自定义角色 | 来自 API，无四种角色硬编码 |
| public、roles: []、指定 roles、继承 | 解释、序列化和最长路径匹配均保持既有契约 |
| 客户端伪造身份头 | 无法获取受保护身份 |
| 更新被用户拒绝或 API 写入失败 | 原配置不变，Agent/UI 不报告成功 |

测试覆盖规则纯函数、权限编辑组件、Cloud API 路由/仓库、introspect schema/转发以及网关。至少包含模拟存储的写入后真实读回测试，不能只断言一个生成的 JSON；角色变化测试复用同一登录会话。跨端由既有 API 兼容测试确认，不要求修改 iOS/Expo UI。

平台集成验证使用隔离测试夹具。不得写入 app7/app6 的线上权限来完成本次验收，不触发其应用部署。

## 9. 交付与上线

交付：平台代码、OpenAPI、针对上述契约的回归测试、deploy-app 指导更新和已验证的 dev 结果。所有旧规则按需读取，无全库迁移或批量重新保存。

顺序：先部署兼容读取/新工具的 Cloud API，再使用更新的 desktop/introspect/skill；现有客户端、已部署应用和旧 audience 规则继续可用。部署平台服务遵循既有授权流程，与修改应用权限分开。

回退：回退平台版本不改变既有 authRules；不以重写规则作为回退步骤。具体实现拆分、测试命令、分支及上线操作由用户批准规格后编写的实现计划确定。

## 10. 明确排除

- app7/app6 的 STAFF_* 变量、代码、员工 API 和重新部署。
- 自动给创建者授权、将员工身份等同于创建者或管理员。
- 修改组织系统角色、删除 finance/owner，或重构 team 与 org 的成员模型。
- 给 Agent 新增组织角色写入、成员角色分配权限。
- 自动将旧 audience 规则批量迁移到固定 roles。

即使本次平台修复完成，app7 当前应用内的拒绝仍会存在；其修复留给后续明确授权的 TeamClu Agent 应用工作。
