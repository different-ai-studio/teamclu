## 实现结果

新增管理员专用 `POST /v1/apps/:appId/undeploy`，以持久生命周期操作串行清理 HTTP Trigger、源站域名映射、FC 函数、唯一构建产物和旧登录客户端。App、代码仓库、工作区、会话、数据库、业务 secrets、上传文件及权限配置保留。202 仅表示接受；各项成功才报告已卸载。

网关立即读取最新生命周期状态，卸载相关状态返回不可缓存的 503。未部署过的应用仍使用原有 404 语义。定时任务保留定义，离线时不调用应用。重新部署可使用保留的成功部署配置作为历史信息，不能将其显示为正在运行的供应商读回。

Web/桌面提供确认和分项进度；Agent 使用绑定的 App、服务端管理员鉴权和独立原生确认，Full Access 不跳过确认。`deploy-app` 保持全英文并说明卸载、重试、重新部署及验收边界。

## 实施决策

1. 文档使用现有可跟踪的 `docs/specs`；忽略的目录不承载交付物。若惯例改变，需要移动文档。
2. 当前没有暴露可用 Supabase MCP；按仓库要求不以 CLI/REST SQL 替代在线迁移。成本是线上验收必须等待 MCP 设置。
3. 当前平台登录使用网关/GoTrue，已不依赖每 App OAuth 注册；卸载仅禁用遗留客户端，不重建旧登录架构。若恢复旧架构，须补客户端恢复步骤。
4. 两种部署环境共用已有认证 cron heartbeat；清理和业务任务共享其请求时间窗口，不增加定时器、路径或密钥。该 heartbeat 停止时清理也暂停。
5. 租约到期不足以证明供应商删除已结束：未知结果保持围栏，明确显示需运维核实；已知失败允许串行重试。成本是超时或进程中断后不自动猜测恢复，需核实资源和操作结果。
