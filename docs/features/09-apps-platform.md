## 0. 一句话定位

**App 是 TeamClu 里第一个「能部署出去」的对象。** 其他资产（知识库、技能、会话）都活在 TeamClu 内部，而 app 会变成一个对外的、有 URL 的网站。这个性质决定了它的所有设计：它需要有代码仓库、需要构建、需要部署目标、需要数据库、需要登录、需要权限、需要删除时的资源回收。

App 的骨架是三个 1:1:1 的对象：

```
app : workspace : git 仓库 = 1 : 1 : 1
```

但反向不成立：一个 workspace **不一定**有 app。现有的纯团队 workspace 照旧，不受影响。

## 1. 从「侧栏里的一个列表」到一等公民

Apps 最初是「侧栏里的一个列表」，落地后暴露的问题不是发布链路，而是 **app 在产品里没有位置**：

- 一个 app 只能有一个 session（`lib/app-session.ts` 注释：`An app has exactly one session for now`）；
- 除了创建者，团队里没有第二个人能动它（凭证、部署、finalize 三处都是 creator-only）；
- 它的 8 个操作全挤在侧栏一行的下拉菜单里，其中「删除」和「本地预览」是 `comingSoon` 空壳；
- 删除没有后端，每个 app 都在往外漏资源。

于是有了「Apps 提升为一等公民」这轮设计。它做了五件事：

1. **信息架构**：Apps 在第一列常驻并可展开；
2. **权限分级**：`view` / `prompt` / `admin` 三档，放开 creator-only；
3. **多会话**：一个 app 可以有多个 session，不再强制 1:1；
4. **删除后端**：真正回收外部资源；
5. **控制面**：从「什么都摊在 280px 里」改成「摘要行 + 中间 tab」。

外加后续几轮补的能力：数据浏览器、文件存储、登录与自定义域名、云端定时任务。

## 2. 信息架构

### 2.1 第一列：Apps 常驻并可展开

- Apps 在第一列内联展开应用列表；「新建」放在标题行后面。
- **只有 Apps 可展开**，会话/知识库/技能等不展开。
- **展开 ≠ 选中**：点标题行切换第二列，点三角展开/收起。
- 折叠状态存 `localStorage`，**per-device 不同步**（它是「我这块屏幕多宽」的偏好）。
- 选中的 app 变化时**自动展开并滚动到它**；用户手动收起后保持收起，直到下一次选中变化。

「只有 Apps 可展开」的判据是：Apps 的子项有独立身份（每个是一个 workspace + 一个部署目标），而其他模块的子项就是第二列本身——把第二列搬进第一列只是白白挤掉空间。

这是一个值得记住的判据。新增模块时问「它的子项有没有独立身份」，就能决定它该内联展开还是只做一行。

### 2.2 第二列：当前 app 的 session 列表

`AppsListColumn` 被删除。第二列的 `apps` 分支改为渲染该 app 的 session 列表。

理由：保留它会造出「第二列有两个形态、两套空状态」，而第一列已经完整呈现了应用列表——同一份数据在两列里各画一遍。

### 2.3 操作分层

| 位置 | 操作 | 判据 |
|---|---|---|
| 第一列行内（悬停/右键） | 部署、打开部署地址、在 Finder 打开 | 看着行上的状态点就能决定 |
| 控制面 | 重命名、Reseed、移动目录、登录方式、权限、删除 | 需要看当前状态和后果才能决定 |

分层原则：**能看着状态点决定的操作放行内，需要上下文才能决定的放控制面。**

### 2.4 控制面是独立 surface

- **不进 `RightPanel`**。现有的 5 个 tab 全是**会话尺度**的；app 设置是**应用尺度**的，混进去会产生「切到别的 session 这个 tab 还在不在」的问题。
- 右上角新增 icon，与 `RightPanel` **互斥显示**，共用同一侧宽度。
- 判定：**「第一列当前选中的 app」`??`「当前 session 的 `appId`」**。
- **不按 workspace 路径判定**——那会让任何碰巧打开了该目录的人看到应用设置。

允许「第一列选中」是因为存在一个必然出现的中间态：点开 app → 第二列列出 session → 用户还没进任何一个，而这恰恰是最想看设置的时刻（刚建完）。

## 3. App 与目录

### 3.1 目录由 daemon 派生，不做创建时选目录

`app-session.ts` 记录了这条规矩的来历：桌面端曾自己算 `~/.amuxd/apps/<id>`，daemon 的根一挪，两边算出不同目录，**agent 在改 A、deploy 在打包 B，线上站点一直是没动过的模板，全程无报错**。

现在的解法是「只有 daemon 知道路径，其他人问它」。

**创建时让用户选目录会把「路径有两个来源」重新引进来**，此外还有三处具体冲突：seed 要把模板写进该目录；`app_clone` 拒绝往非空目录 clone；build 要在那里跑 `pnpm install`。

这个 bug 的形态值得记住：**两个组件各自算同一个路径，且都不报错。** 与第 4 篇的「三处白名单镜像」、第 7 篇的「两套并存」是同一类问题的不同外观。

### 3.2 取而代之：控制面提供「移动到…」

- **真搬整个目录**（含 `.git` 与 `node_modules`）：同盘 `rename`，跨盘 `copy + verify + delete`；**失败保留原目录且不改指针**。
- 只改指针不搬文件是不行的：旧目录仍在磁盘上，agent 的历史上下文指向老路径，`node_modules` 要重装。
- 路径覆盖存 **daemon 本地** `config::layout::team_state_dir(team_id)` 下的一个小 json；`resolve_workdir` 先查它再走派生——「单一来源」仍然成立，只是那个来源多了一层本机覆盖。

### 3.3 `workspaces.path` 的定位要降级

`workspaces.path` 是**全局一列**，而同一个 app 在两台机器上的目录本来就不同（`AMUXD_HOME`、brand 都会变）。今天没出事，是因为运行时**从不信这一列**，永远问 daemon。

- 云端该列**降级为「最近一次某设备报告的路径」**，不是权威。
- UI 上明确标注 **「本机路径」+ 设备名**。
- 这样「移动」天然是每台机器各自的事。

## 4. 会话、并发与权限

### 4.1 一个 app 多个 session

废除「exactly one session」，第 N 个由用户显式创建（不自动开）。**不做运行态互斥**（明确决定：太复杂）。

### 4.2 唯一的并发防线：部署前确认

取消互斥意味着两个 agent 可以同时写同一个目录，而那个目录随时会被 `pnpm build` 打包上线——打出来的是两份改动的任意中间态，且**全程没有任何报错**。

- 在**点部署那一刻**查一次该 workspace 有没有活跃 turn（`workspace_has_active_turn`，已存在）。
- 有活跃 turn 则弹确认（复用 `publicDeployConfirm` 的形状），**只确认不硬拦**。
- 这是一个检查点，不是并发模型。

「只确认不硬拦」是一个有意的选择：真正阻止用户会让他觉得工具在碍事，而他要的只是「知道现在有风险」。这与知识库的「大批新增被拦下」不同——那里的后果是团队级数据污染，这里是「可能打出一个中间态」，用户能自己判断。

### 4.3 权限模型

授权主体是 **member，不是 session participant**。`app_member_access` 表已经存在，`listApps` 已在读它。

**不用 session participant 作主体**，两条理由：

1. `session_participants.actor_id` 指向 actors，而 actor 包含 member / agent / external。一个从企业微信进到会话里的人拿「repo 写权限」没有落点——他没有机器、没有 daemon、没有 git 客户端。
2. 一个 app 可以有多个 session，权限跟着 session 走就意味着**「把人拉进一个会话 = 授予 repo 权限」**。拉人进会话是个很轻的动作，把它变成授权路径太容易误触。

**分工**：`visibility` 管**可见性**；`app_member_access` 管**可写性**。

### 4.4 三档如何映射到 git

| 档位 | 凭证 | 能做 | 不能做 |
|---|---|---|---|
| `view` | 不发 | 看 | 拿代码 |
| `prompt` | **写** deploy key | clone、让 agent 改、commit、push | 部署、授权 |
| `admin` | **写** deploy key | 以上全部 + 部署 + 授权 + 改 authMode | — |

**这里推翻了一个初始建议。** 最初建议 `prompt → 只读 key`（「agent 干活要读代码」）。把它和「按需 clone」拼起来会造出一条死路：**agent 改完代码，人推不上去**——那份工作永远留在他的磁盘上，远端看不到、owner 看不到，他自己下次想部署还会被 `ERR_DIRTY` 拦住。这不是一个能解释给用户听的权限。

正确的切法是把闸移到**上线**：改代码和把它送上线本来就是两个动作，真正不可逆、对外的是后者。这也让 `prompt` 这个名字重新说得通。

不新增 git 维度、不造第二套权限模型——否则控制面里要同时展示两组开关，用户得自己想明白它们的交集。

### 4.5 owner 是 TeamClu 层的概念

- 「我建的 app、我决定谁能改」由 `apps.created_by_actor_id` + `app_member_access` 表达。
- **仓库仍归单一 bot org，不给用户开 Gitea 账号。**
- 用户在那个 Gitea 上没有账号，他对仓库的唯一通路是我们按权限发的 deploy key。这是特性不是缺陷：不需要记第二套账号密码。

### 4.6 第二个人的代码从哪来：按需 clone

app 的 workdir 是本机路径，**只有创建者那台机器上有 checkout**。B 拿到权限后他的 daemon 会算出一个路径，但那个目录是空的。

- **B 第一次打开该 app 时按需 clone**（`clone_app_repo` 已存在，导入外部仓库那条路在用），凭证按档位发。
- 每人一份本地 checkout，各自 commit / push。
- B 本地有未推送改动时，复用现有的 `ERR_DIRTY` 闸。

## 5. 身份与归属

### 5.1 现状：两层都是空的

- **commit 作者写死**：`app_git.rs` 是 `TeamClu <apps@teamclu.local>`，且用 `-c` **只作用于 seed 那一次 commit**。之后 agent 或用户在 workdir 里提交，用的是**那台机器的全局 git config**——可能是本人、可能是同事借的机器、也可能压根没配。所以 `git log` 里现在是：第一条 "TeamClu"，后面若干条身份完全不受管。
- **push 匿名**：`jitDeployKeyTitle` 只有 `jit-<ts>-<nonce>`，不带调用者信息。
- 但**服务端在发凭证那一刻已经知道是谁**，只是没拿它命名 key。

### 5.2 两层都补，都不需要 Gitea 账号

1. **commit 身份**：seed 时把 `user.name` / `user.email` 写进该仓库的 **repo-local `.git/config`**（取当前 TeamClu 用户）。此后 agent 和用户的每一次 commit 自动带上——这正是今天用 `-c` 做不到的。
2. **push 身份**：key 标题从 `jit-<ts>-<nonce>` 改为带 `actorId`。Gitea 的仓库审计能看出是谁的 key 推的，也给撤权提供抓手。

### 5.3 撤权即撤 key

撤掉 `app_member_access` 那一行只能挡住**下一次**发凭证；对方手上那把私钥对应的公钥还挂在仓库上，照样能推。今天 `expiresAt` 的 15 分钟纯粹是文案，实际清理只发生在「下一次有人给这个 app 要凭证」的 sweep 里——没有下一次就永远不清。

- **撤权时立刻按 `actorId` 删掉他在该仓库的所有 key**，不等 TTL。
- 保留过期 sweep 作兜底。
- **UI 必须写明**：对方本地那份 clone 撤不回来。撤权只能阻止他继续推送和拿到新代码，**已经在他磁盘上的代码就是在他磁盘上了**。

这条与第 5 篇的 Path ACL「撤权只承诺停止同步，不承诺收回」是同一条纪律。任何「撤权」都会有这个边界，区别只在于说不说清楚。

## 6. 生命周期

### 6.1 创建

创建 app 时：建 `apps` 行、建 1:1 的 workspace、开 git 仓库、daemon 播种模板（首个 commit）。`provision_status` 状态机驱动这个过程，失败原因写进 `provision_error` 给 UI。

### 6.2 部署

部署链路：FC 函数 + HTTP 触发器、OSS 上的 `code.zip`、GoTrue OAuth client、Postgres schema 与角色。

几个关键点：

- **构建产物**：`apps/<appId>/code.zip`，daemon 用 30 分钟有效的预签名 PUT 上传，FC 从同一个 key 读代码。
- **凭证档位**：deploy key 按 `app_member_access` 发。
- **authMode 注入**：OAuth 的 env 是在 `finalizeDeploy` 里由 `buildPlatformOAuthEnv` 注入函数的。

### 6.3 authMode 改动不立即生效

把一个**已上线**的 app 从「无登录」改成「平台登录」，云端行改了，**线上函数仍是旧 env，站点依然全公开**——直到下一次重新部署。

- 改完立刻把该 app 标为**「待重新部署」**，并在保存按钮旁给**「立即重新部署」**。
- **这条不能静默**：用户刚点完「需要登录」，会认为站点此刻已受保护，而实际没有。这是安全预期落空，比功能不生效严重。

### 6.4 删除：删什么、留什么

**真删**（是我们替用户开的，删 app 就该收回）：FC 函数 + HTTP 触发器、OSS 上的 `code.zip`、GoTrue OAuth client。

**保留**：

- **Postgres schema 与角色**——里面是用户自己的业务数据，删了不可逆而我们没有备份。
- **本机目录**——是用户的工作副本；删别人磁盘上的东西要单独勾选同意。
- **Gitea 仓库**——但要**撤掉该仓库上所有人的 key** 并 **archive 成只读**。留着任何一把活的写 key 都是无主的口子；archive 让「保留」变成一份不可写的代码快照。改名加 `deleted-` 前缀，仓库地址记进那行被归档的 workspace。

**顺手归档那行会变孤儿的 workspace**（`apps.workspace_id` 是 `ON DELETE SET NULL`，删 app 不删 workspace）。

### 6.5 删除对话框的措辞

**不要写「代码已为你保留」**——用户没有 Gitea 账号，会以为自己能拿到。写：

> 代码不会被删除，但删除后你将无法从 TeamClu 访问它；需要找回请联系管理员。

同时说清楚「站点会立刻下线、数据库保留」。

## 7. 数据浏览器

`AppDataBrowser` + `AppDataTabContent`：在控制面里浏览 app 的线上 Postgres 数据。打开某个表会在主列开一个 tab（`openAppDataTable`）。

它的价值是：**用户不需要 psql 就能看到自己的数据。** 对一个「让非工程师也能建应用」的产品，这是把「应用是否真的在工作」变得可验证的关键。

## 8. 文件存储

每个 app 有一块 OSS 空间（`docs/specs/2026-09-09-app-storage-design.md`）：控制面能浏览/上传/下载/删除，部署后的 app 运行时能读写自己那块。

关键设计：

- **一个 bucket、每 app 一个前缀。** 线上实际是两个 bucket（`teamclu-app` 与 `teamclu-self-host-storage`），app 文件落在 `teamclu-app`——也就是 apps profile 解析出来的那个，与 `code.zip` 同 bucket 不同顶层前缀。
- **apps 用的是独立 profile**，不是默认那把。因为 apps profile 和默认 profile 在 self-host 上可以是两套凭证、两个 endpoint，跨过去就会 403。
- **配额**：实测并修正过两处初稿结论。
- **删除语义**：与 app 删除一起定义。

「一个 bucket、靠前缀分隔租户」是仓库已表过态的原则（`team-blob-storage.ts` 注释），但要注意它说的是「同一个 bucket 内靠前缀分隔租户」，不是「全世界一个 bucket」。

## 9. 控制面重排与新增能力

`docs/specs/2026-09-10-app-control-panel-design.md`：右侧控制面从「什么都摊开在 280px 里」改成「一行一件事、带个数、点右箭头去中间 tab 管」，并补上两块能力：

1. **每个页面各自的登录与受众**。此前 `auth_audience` 是应用级的一个值（any / org），路径规则只有 `required | public` 两档——「/admin 只给员工，/ 给任何用户」表达不了。
2. **应用的云端定时任务**。注意这与第 8 篇的 cron 不同：桌面 cron 是按 workspace 路径分实例的 agent 定时任务，跟部署出去的站点无关。云端一侧，`stripe-reconcile.ts` 注释里写着「cron 任务」，但仓库里**没有任何调用方**——那是手工在阿里云 FC 上建的两个定时函数。也就是说云端调度器要从零做。

明确的非目标：**角色**。终端用户身上没有任何角色概念（网关只透传 user id / email / orgId），做角色要新表 + 授权界面 + 网关比对。`员工/用户` 这一档就是受众。

## 10. Config in code

`docs/specs/2026-08-27-apps-config-in-code-design.md`：app 的配置以代码形式存在（而不是全在云端行），这样它能被版本化、被 agent 改、被 diff。

这条与「控制面」是互补的：控制面提供便捷入口，配置文件是权威。改动要能从两边一致地生效。

## 12. 常见坑

1. **app : workspace : git = 1:1:1，但 workspace 不一定有 app。**
2. **目录只能由 daemon 派生。** 不要在任何地方自己拼路径。
3. **`workspaces.path` 不是权威。** 它是「最近一次某设备报告的路径」。
4. **`prompt` 是写权限。** 只读 key 会造出「改完推不上去」的死路。
5. **撤权要立刻删 key。** 不要等 sweep。
6. **撤权不能收回已 clone 的代码。** UI 要写明。
7. **authMode 改动要标「待重新部署」。** 否则安全预期落空。
8. **删除时 Gitea 仓库要 archive + 撤所有 key。** 留一把活 key 就是无主的口子。
9. **删 app 不删 Postgres 数据。** 那是用户的业务数据。
10. **`features.apps` 关闭只是没有入口。** 数据照常可用，已部署站点还活着。

## 13. 附录 A：app 的类型系统

`apps.type` 是一个枚举，第一期只支持 `fullstack_tanstack_postgres`（TanStack 前端 + Postgres 后端）。`app-types.ts` 与 `app-type-icon.ts` 负责前端的类型展示。

为什么第一期只做一种类型？因为一种类型就能把整条链路走通：仓库、模板播种、构建、部署、数据库、登录。多类型会把这些环节弄成参数化的，而参数化需要至少两个真实实例才能知道哪些确实是差异。

这个决定与本仓库其它地方的思路一致：**先让一条路完全跑通，再把它参数化。** 多 runtime 的教训（ADR-0014 从 4 个收敛到 1 个）说明反过来做的代价很大。

新增一种类型时，至少要确定：

- 模板仓库是什么；
- 构建命令是什么；
- 部署目标是什么（FC？静态托管？）；
- 是否有数据库，哪种；
- 登录方式是否相同；
- 文件存储是否相同。

这六个问题的答案如果与现有类型在四个以上相同，那么「新类型」可能只是同一个类型的一个模板变体。

## 14. 附录 B：创建与 provision 状态机

创建 app 不是一个事务，而是一串外部调用。`provision_status` 就是这个过程的状态：

```
pending
  → 建 DB 行 + workspace
  → 建 git 仓库
  → 播种模板（首个 commit）
  → 成功 → ready
  → 失败 → error（provision_error 写原因）
```

为什么要有状态而不是「一步到位」？因为中间任何一步都可能失败（Gitea 不可用、OSS 权限不对、网络超时），而用户需要一个可重试、可解释的状态。`provisioning/app-deploy.ts` 与相关模块是这个状态机的实现。

一个具体的失败模式值得知道：**Gitea 目前没有部署时，建 app 会 503 `gitea_unavailable`。** 前稿那整套在线上是暗的。这也是「先部署 Gitea，再做信息架构」的实施顺序的理由——控制面里好几块行为只有在真能建 app 时才验证得了（移动目录、删除时撤 key、authMode 改完要重新部署），拿更早路径建出来的 app 去验，验的是空壳。

这条教训值得记：**一个依赖外部服务的功能，在外部服务不存在时看起来「实现了」而实际是「暗的」。** 单元测试能过，因为没有它也能跑；而真正的回归只有在服务活了之后才会出现。

## 15. 附录 C：部署链路的细节

部署是 app 生命周期里唯一「对外生效」的一步，所以它最值得细看。

### 15.1 代码怎么上去

1. daemon 在 app 的 workdir 里构建；
2. 产物打包成 `code.zip`；
3. 用 30 分钟有效的预签名 PUT 上传到 OSS 的 `apps/<appId>/code.zip`；
4. FC 从同一个 key 读代码。

注意「预签名直传」这个模式与知识库同步一致：字节不经过 FC。好处是 FC 不成为带宽瓶颈，代价是「上传完成」需要一次 HEAD 校验才能确认（与市场发布 API 的 ③ 步是同一个模式）。

### 15.2 函数与触发器

FC 函数 + HTTP 触发器是这个 app 的运行时。函数名、region、endpoint、status 都在 `apps` 表里。

### 15.3 数据库

Postgres：为 app 建 schema 与角色。删除时**保留**，因为里面是用户的数据。

### 15.4 登录

GoTrue OAuth client。`authMode` 决定站点是否需要登录，`auth_audience`（any / org）决定受众，`auth_rules` 是按路径的规则（required / public）。这些 env 在 `finalizeDeploy` 时注入。

### 15.5 一个必须记住的不对称

**部署是幂等的，但它的副作用不是。** 重新部署会换掉函数的 env、重建触发器、重新注入 OAuth 配置。如果这次部署比上一次少了某个配置（比如用户改了登录方式），线上的行为会变——而且不会有人提醒。这就是为什么 authMode 改动要显式标「待重新部署」（第 6.3 节）。

## 16. 附录 D：数据浏览器的实现

`AppDataBrowser` 打开一个表时会调用 `openAppDataTable(app, table)`，它把 target 编码成 `app-data:<appId>/<table>`，`TabContentRenderer` 解析后渲染 `AppDataTabContent`。

几个设计点：

- **一个表一个 tab。** 用户可以同时看两个表。
- **主列而不是侧栏。** 看数据需要空间，也知道用户会一边看应用一边对照。
- **`app-data-cell.ts` / `app-data-row-key.ts`** 处理单元格渲染与行键，说明它面对的是任意 schema 的数据——不能假设列类型。
- **日志也在主列 tab**（`app-logs:<appId>`）。注释写明了原因：读日志意味着滚动大量文本、会改变窗口，而「为什么线上挂了」通常在站点本身旁边被问——站点也是一个 tab。

一个与第 10 篇的关系：数据浏览器是一个「给非工程师用的数据库界面」，而第 10 篇的编辑器是「给工程师用的代码界面」。两者都在同一个三栏壳里，用同一套 tab 机制。

## 17. 附录 E：文件存储的边界

app 文件存储（`docs/specs/2026-09-09-app-storage-design.md`）有几个决策值得展开。

### 17.1 为什么用 apps profile 而不是默认 profile

`resolveAppsOss()` 解析出一个 `AppsOssProfile`。在 self-host 上，apps profile 与默认 profile 可以是两套凭证、两个 endpoint。如果 app 文件用了默认 profile 的凭证去写 apps profile 的 bucket，结果就是 403。

这是一个容易踩的坑：**「同一个云厂商」不等于「同一套凭证」。** 代码里有两个 profile 是因为部署上真的可能是两套，而不是历史冗余。

### 17.2 key 布局

```
teamclu-app/
  apps/<appId>/code.zip         构建产物
  apps/<appId>/...              app 的用户数据
```

同一个 bucket、不同前缀。注意这与团队 blob 的是另一个 bucket（`teamclu-self-host-storage`）——「一个 bucket」这句话要按「同一个 bucket 内靠前缀分隔租户」理解。

### 17.3 明确的非目标

图片处理与缩略图、CDN 与自定义分发域名、跨 app 共享文件、对象版本历史、本地开发时的存储模拟、把团队知识库的 blob 迁进来。

这份「不做」清单很具体，它的作用是防止后续把存储层扩成一个通用文件系统。**一个通用的文件存储会吸引所有需要存东西的功能，而其中大多数应该用别的方式解决。**

## 18. 附录 F：登录、受众与自定义域名

### 18.1 三层控制

| 层 | 值 | 作用 |
|---|---|---|
| `authMode` | 无登录 / 平台登录 | 站点是否需要登录 |
| `auth_audience` | any / org | 谁能登录 |
| `auth_rules` | 按路径 required / public | 哪些路径需要 |

`docs/specs/2026-09-10-app-control-panel-design.md` 指出：这套只能表达「全站要登录」或「全站公开 + 个别路径」，而「/admin 只给员工，/ 给任何用户」需要**每条路径各自带受众**。这是控制面重排里补上的能力。

新增的是「路径规则带受众」，而不是「角色」。区别很重要：角色是终端用户身上的属性（需要新表 + 授权界面 + 网关比对），受众是路径上的声明（只需看当前请求的用户是否属于某个集合）。后者能在现有网关透传的 user id / email / orgId 上做，前者不行。

### 18.2 自定义域名

`AppCustomDomainSection.tsx`。它涉及 DNS 与证书，所以不是一个纯前端功能。

### 18.3 与 authMode 的交叉

自定义域名 + 登录受众组合起来时，redirect URL 的域名必须跟着变。这是部署时 OAuth client 配置的一部分，也属于「改了要重新部署」的范畴（第 6.3 节）。

## 19. 附录 G：应用的云端定时任务

这是一个容易与第 8 篇混淆的能力。区别：

| | 桌面 cron（第 8 篇） | 应用云端定时 |
|---|---|---|
| 对象 | agent 的定时回合 | 部署出去的站点 |
| 触发 | 桌面/daemon 调度器 | 云端定时器发 HTTP 请求 |
| 执行 | agent turn | 站点的 HTTP 端点 |
| 依赖 | 本机 daemon | 不需要本机开机 |

应用定时任务的用途：每天凌晨清理过期数据、每小时同步一次外部订单、定期发报表。它们都应该在**云端跑**，因为「本机关机照跑」是这个能力存在的理由。

现状：**云端调度器要从零做。** `stripe-reconcile.ts` 注释里写着「cron 任务」，但仓库里**没有任何调用方**——那是手工在阿里云 FC 上建的两个定时函数，不在这个仓库。

这是一个重要的事实记录：**代码里有注释说「这是 cron」，不代表这个 cron 是被这个仓库管理的。** 后来接手的人容易以为它已经实现。

## 20. 附录 H：权限矩阵与 UI

把 app 相关的权限动作汇总：

| 动作 | view | prompt | admin | owner（created_by） |
|---|---|---|---|---|
| 看 app / 看会话 | ✅ | ✅ | ✅ | ✅ |
| 拿到代码（clone） | ❌ | ✅ | ✅ | ✅ |
| 改代码 / commit / push | ❌ | ✅ | ✅ | ✅ |
| 部署 | ❌ | ❌ | ✅ | ✅ |
| 授权给别人 | ❌ | ❌ | ✅ | ✅ |
| 改 authMode | ❌ | ❌ | ✅ | ✅ |
| 删除 app | ❌ | ❌ | ❌ | ✅ |

这张表对应四个地方，改动时必须一致：

1. `pg-repo/apps.ts`（应用层，postgres 后端没有 RLS 可依赖）；
2. RLS 迁移（supabase 后端）；
3. 前端按钮的可见性；
4. 授权对话框的文案。

第 4 条容易被忽略：**授权 UI 必须说清「撤权不能收回已 clone 的代码」**，否则 owner 会以为「撤权 = 代码收回」（第 5.3 节）。这与第 5 篇 Path ACL 的措辞纪律是同一件事。

## 21. 附录 I：实操：从零建一个 app 并部署

把流程走一遍，能看到各部件如何配合。

**第一步：创建。** 第一列 Apps 点「新建」，`CreateAppView` 填名称，选类型。提交后云端建 `apps` 行 + workspace，服务端 provision git 仓库，写 `provision_status`。

**第二步：播种。** daemon 把模板写进该 app 的 workdir，做第一个 commit（带 repo-local 身份）。用户在第一列看到这个 app，点开看第二列它的 session 列表。

**第三步：开发。** 创建一个 session，agent 在 workdir 里写代码。用户可以在编辑器 tab 里看文件、看 diff。

**第四步：部署。** 行内点部署。这时会查该 workspace 有没有活跃 turn（第 4.2 节）；有则弹确认。确认后 daemon 构建、打包、上传 `code.zip`，FC 读代码并更新函数与触发器与 OAuth env。

**第五步：验证。** 控制面的「打开部署地址」在 webview tab 里打开站点；数据浏览器 tab 看数据库；日志 tab 看运行日志。

**第六步：协作者。** owner 在控制面给 B 授 `prompt`，B 第一次打开时 daemon 按需 clone。B 本地改、commit、push，然后（如果有 `admin`）部署。

**第七步：删除。** owner 在控制面删除，看到明确的「代码保留但无法访问、数据库保留、站点下线」措辞，确认后云端真删 FC/OSS/GoTrue，保留 Postgres 与 Gitea（archive + 撤 key）。

这条流程里最容易被低估的是第六步。它把前面所有权限设计都串了起来：授权主体、凭证档位、按需 clone、push 身份、撤权即撤 key。任何一环做错，表现都是「B 用不了」或更糟的「B 能用到不该用的」。

## 22. 附录 J：与其它模块的关系

| 模块 | 交界 |
|---|---|
| 会话 | 每个 app 有若干 session；app session 带 `app_id` |
| Agent runtime | agent 在 app 的 workdir 里干活 |
| 团队 | app 属于团队；权限主体是 member |
| 权限 | `app_member_access` 三档 |
| 存储 | OSS 的 app 前缀 + `code.zip` |
| 模型 / LLM | agent 开发时用的模型（不特殊） |
| 知识库 | 不直接相关（app 的文档可以放资料库） |
| 网关 | 不直接相关 |
| 定时（第 8 篇） | 桌面 cron 是 agent 的；云端定时是站点的 |

一个容易搞混的边界：**app 的 session 与普通 session 的区别只是多了一个 `app_id`。** 它们用同一套聊天 UI、同一套消息模型、同一套权限（session 参与者）。app 权限管的是 repo 与部署，不是聊天。

这个区分很重要：如果把它们混起来，就会出现「把人拉进会话 = 给他 repo 权限」的误解——而这正是第 4.3 节明确否掉的设计。

## 23. 附录 K：常见问题

**Q：app 和 workspace 是什么关系？**
A：1:1。但 workspace 不一定有 app，现有的纯团队 workspace 照旧。

**Q：app 的代码存在哪？**
A：每个成员的机器上各有一份 clone；权威在 Gitea。

**Q：为什么我看不到 B 的 app 设置？**
A：控制面判定是「第一列选中的 app」或「当前 session 的 appId」，**不按 workspace 路径**。所以碰巧打开了同一个目录并不等于能看到设置。

**Q：`view` 权限能拿到代码吗？**
A：不能。`view` 不发凭证。

**Q：`prompt` 能部署吗？**
A：不能。`prompt` 是写代码与 push，部署是 `admin`。

**Q：撤权后对方还能推吗？**
A：不能，因为我们立刻删了他在该仓库的所有 deploy key。但他本地已有的代码收不回来。

**Q：删除 app 会删数据库吗？**
A：不会。Postgres schema 与角色保留。

**Q：删除 app 会删 Gitea 仓库吗？**
A：不会真删，但会 archive 成只读并撤掉所有 key。

**Q：为什么改了登录方式站点还是公开的？**
A：因为 env 在部署时注入，改完要重新部署。控制面会标「待重新部署」。

**Q：`features.apps` 关掉会怎样？**
A：只是没有入口。数据、workspace、已部署站点都还在。

**Q：一个 app 能有几个 session？**
A：任意个，第 N 个由用户显式创建。

**Q：两个 agent 同时改会怎样？**
A：没有互斥，但部署前会检查活跃 turn 并让你确认。

## 25. 附录 M：六条不变量

1. **目录只有一个来源：daemon。** 任何地方自己拼路径都会重演「agent 改 A、部署打包 B」。
2. **`prompt` 是写权限，不是只读。** 只读会造出「改完推不上去」的死路。
3. **撤权立刻删 key，但收不回已 clone 的代码。** 后者要写在 UI 上。
4. **删除保留数据（Postgres、本机目录）与仓库（archive）。** 只收回我们替用户开的资源。
5. **authMode 改动必须标「待重新部署」。** 安全预期不能落空。
6. **`features.apps` 只控制入口，不控制数据。**

这六条对应了本文里六处看起来保守的设计。它们共同的特征是：**它们的反面都能让系统「看起来在工作」，但结果是错的。** 这正是 Apps 比其它模块更需要这些约束的原因——它面对的是不可逆的对外副作用。

## 26. 附录 N：改动检查清单

1. 新增操作时，权限档位定在哪一档？四个地方（应用层/RLS/UI/文案）都改了吗？
2. 新路径是不是又产生了第二个来源？
3. 新动作是不是不可逆的？如果是，需要确认对话框吗？
4. 新动作会改线上行为吗？需要标「待重新部署」吗？

9. 新的 bucket/profile 用的是对的那一套凭证吗？
10. 关掉 feature flag 后数据还可达吗？

## 28. 附录 P：为什么「不可逆」是这块的核心

把 Apps 与其它模块放在一起看，会看到一个清晰的分界：

| 模块 | 最坏情况 | 可逆吗 |
|---|---|---|
| 会话 | 消息发错了 | 可解释、可补充 |
| 知识库 | 文件冲突/误删 | 有版本历史，能恢复 |
| 技能 | 装了不好的 skill | 卸载即可 |
| 通道 | 回复错了 | 可更正 |
| **Apps** | **线上站点泄露数据 / 代码被删 / 资源漏计费** | **不可逆** |

最后一行决定了 Apps 的设计风格：它几乎每一个重要决定都在回答「这个动作能不能收回」。

- 部署前确认（第 4.2 节）：因为打包中间态上线是外部可见的。
- authMode 标待部署（第 6.3 节）：因为「以为已受保护」比「没受保护」更危险。
- 删除保留 Postgres（第 6.4 节）：因为我们没有备份，删了就是没了。
- 撤权撤 key（第 5.3 节）：因为一把活 key 就是一个永久入口。
- archive 而不是 delete Gitea（第 6.4 节）：因为保留一份不可写的快照比彻底删除安全。

这五条没有一条是「更好的工程实践」，它们都是**对不可逆性的直接回应**。换一个可逆的领域，这五条都可以不做。

---

## 29. 附录 Q：与其它模块的横向对比

一个有用的练习：把「资源所有权」这个概念在四个模块里对齐。

| | 谁拥有 | 删除时 | 撤权时 |
|---|---|---|---|
| 知识库 | 团队 | 删行 + tombstone | 停止同步，不收回 |
| 技能 | 团队 | 删注册表行，已装的靠对账卸载 | 卸载 |
| 通道配置 | 团队/工作区 | 删配置 | 不适用 |
| **Apps** | 团队，但资源直属于 app | 删我们开的，留用户的 | 删 key，不收回代码 |

一个规律：**「停止分发」永远是能做的，「收回已分发」永远不能。** 知识库的撤权、Apps 的撤权、技能的卸载都是这个形状。原因相同：一旦字节到了别人的磁盘上，任何中心化的系统都无法保证删除。

这条规律在写任何「权限/撤回」功能时都适用。**唯一能承诺的是「不再给你新的」，而不是「把你手上的拿回来」。** 把这个说清楚，比实现它更重要。

---

## 30. 一个总结：三个问题

把整篇压缩成三个问题：

**谁拥有它？** app 属于团队，但它的资源（FC、OSS、Gitea、GoTrue、Postgres）直属于 app 本身。删除时要区分「我们替用户开的」与「用户自己的」。

**谁能改它？** 三档：`view` 只能看，`prompt` 能拿代码、改代码、push，`admin` 能部署与授权。授权主体是 member（不是 session participant），因为「拉人进会话」不能等于「授予 repo 权限」。

**删了之后剩下什么？** 代码保留但不可访问（Gitea archive + 撤 key）、数据保留（Postgres）、本机目录保留、站点下线。

这三个问题的答案决定了本文里所有看起来保守的设计。它们共同的主题是**不可逆性**：app 是 TeamClu 里唯一有对外副作用的对象，所以它第一次需要「删除」这个动作、需要「权限分级」、需要「资源回收」。

最后一个与其它模块共享的规律：**「停止分发」永远能做，「收回已分发」永远不能。** 知识库的撤权、技能的卸载、app 的撤权都是这个形状。唯一能承诺的是「不再给你新的」，而不是「把你手上的拿回来」。把这个说清楚，比实现它更重要。

## 31. 附录：不可逆操作的清单

把本文里所有「做了就收不回来」的动作集中列一遍，作为审核新功能时的对照表。

| 操作 | 不可逆的部分 | 缓解 |
|---|---|---|
| 部署 | 线上站点变了 | 部署前活跃 turn 确认 |
| 改 authMode | 预期与实际不一致 | 标「待重新部署」 |
| 删 app | 站点下线、外部入口断 | 措辞写明、保留数据 |
| 撤权 | 已 clone 的代码留在对方磁盘 | UI 写明 |
| 授权 | 对方能拿到代码 | 三档分级 |
| 改自定义域名 | DNS/证书切换 | 需要重新部署 |

这张表里没有一条是「完全不可逆」的（除了「已 clone 的代码」）。全部都是「需要额外动作才能恢复」或「需要通知受影响的人」。

区分这两种很重要：

- **需要额外动作**：删了 app，重建一个同名的不等于恢复（新 ID、新站点、旧数据要手动迁）。所以它实际上是不可逆的。
- **需要通知**：改了 authMode，重新部署一下就行。但如果没人知道要重新部署，它就是不可逆的。

所以「不可逆」在这块的定义不是「物理上不能恢复」，而是**「用户以为变了但实际没变」**。这正是 authMode 那条比其它条更危险的原因：它不是「做了收不回」，而是「做了却没发生，而用户以为发生了」。

---

## 32. 附录：一个可以复用的判断

这篇的核心判断可以压缩成一句：**「这个动作是内部的还是对外的？」**

- 内部的（改代码、开 session、看数据）：出错了可以重来，权限只需「谁能看」；
- 对外的（部署、删 app、撤权）：出错了收不回，权限需要分级、需要确认、需要措辞。「能部署」是一个对外承诺，它需要比「能写代码」更强的门槛。

这条判断直接解释了本文里两个看起来奇怪的取舍：

1. **`prompt` 给了写权限。** 因为它是对内的；真正的闸在部署。
2. **authMode 要标「待重新部署」。** 因为它是对外的安全预期。

一个实用的方法：新增一个 app 操作时，先问它会不会改变「外部能看到的东西」。会，就需要确认、需要时机提醒、需要在删除时考虑回收；不会，就可以直接做。

## 33. 附录：一句话总结

如果把整篇压成一句话：**app 是 TeamClu 里唯一有对外副作用的对象。**

这一个定位推出了它的全部设计：对外意味着不可逆（所以需要确认与措辞）、意味着资源（所以需要删除与回收）、意味着多人（所以需要权限分级）、意味着真实数据（所以删除时要保留）。

其它模块的「最坏情况」都可以解释、都能恢复；app 的最坏情况是一个线上站点泄露数据，或者一份永远不会再跑的代码。所以它比其他模块更保守，而保守的代价是操作步骤多。这个代价是值得的：宁可多一次确认，不要一次不可逆的错误。

## 34. 附录：最后三条提醒

**一、目录只有一个来源。** 任何地方自己拼路径都会重演「agent 改 A、部署打包 B」。

**二、官方凭证只有一个档位。** `prompt` 是写权限，因为它是对内的；真正不可逆的是部署。

**三、删除要区分「我们开的」与「用户的」。** FC/OSS/GoTrue 删，Postgres/本机目录/Gitea 保留。

三条都是这块历史付过代价的教训。

## 37. 附录：最后一点：不可逆性的代价

App 比其他模块多出那么多约束，本质上是在为「不可逆」付代价。这些约束让操作变慢、让按钮变多、让文案变长，用户可能觉得繁琐。

但另一种选择更贵：一个用户以为「撤权了」却发现代码已经被人拷走、一个用户以为「加了登录」却发现站点还是公开的、一个用户以为「代码保留」却永远拿不到。**信任不是靠功能多少建立的，而是靠每个承诺都成立建立的。**

## 38. 附录：三句话的速记（终）

**app 是唯一有对外副作用的对象；`prompt` 是写权限而闸在部署；删除只收回我们替用户开的资源。**

三句分别对应不可逆性、权限分级、资源所有权。再加一条：`workspaces.path` 不是权威，目录只有 daemon 一个来源。

## 39. 结语

Apps 这块的设计密度看起来很高，但它其实只在回答三个问题：**谁拥有它、谁能改它、删了之后剩下什么。** 其它模块（会话、知识库、技能）也面对这三个问题，但它们的答案都是「留着」——会话不会因为删一个东西而消失，知识库不会因为撤权而收回，技能不会因为卸载而在别人机器上消失。

Apps 不一样。它会真的变成一个有 URL 的网站、一个别人能访问的入口、一份存在云端的代码。所以它第一次需要「删除」这个动作、需要「不可逆」这个概念、需要「我们替用户开的资源」与「用户自己的数据」的区分。理解了这一点，就会明白为什么本文的每一条约束都是在防止「看起来在工作，但结果是错的」。

Apps 是 TeamClu 里唯一「有对外副作用」的对象：它会变成一个真实的网站，有真实的用户，有真实的数据。所以它的设计里第一次出现了「不可逆操作」（部署、删除）、「权限分级」（view/prompt/admin）、「资源回收」（FC/OSS/Gitea/GoTrue）。这些东西在内部的会话与知识库里都不需要——这也解释了为什么 Apps 的设计文档比其他模块长得多：**它面对的不是「数据放哪」，而是「事情做了就收不回来」。**

如果只从本文带走一件事，就带这条判断：**新增一个 app 操作时，先问它会不会改变「外部能看到的东西」。** 会改变，就需要确认、需要时机提醒、需要在删除时考虑回收；不会改变，就可以直接做。本仓库里其它模块的「最坏情况」都能解释、都能恢复，唯独 app 的最坏情况是一个线上站点泄露数据、或者一份永远不会再跑的代码——所以它更保守，而那个代价是值得的。记住：对外的事，慢一点比错一次便宜得多，而这句话在 app 这块尤其成立。
