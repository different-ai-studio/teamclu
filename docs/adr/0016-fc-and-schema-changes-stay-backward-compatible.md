# FC 与数据库改动必须对已发布的 daemon 向后兼容

`services/fc/`（Cloud API）和 `services/supabase/`（schema / RLS / RPC）的任何
改动，默认要保证**已经装出去的 amuxd daemon 继续可用**。用户不会因为服务端发版
就同步升级桌面端，旧 desktop 里的旧 amuxd 会长期在线打 `/v1`。本 ADR 把这条
隐含预期变成显式规则。

## 规则

1. **只增不改。** 新增字段、新增端点、新增可选参数是安全的；改字段语义、改类型、
   改必填性、删字段、改默认值都不安全，除非先走第 3 条。
2. **旧形状保留并标 `deprecated`。** 一个字段被新字段取代时，旧字段继续返回、
   继续接受写入，并在 `docs/openapi/teamclu-api.v1.yaml` 上标
   `deprecated: true` 写清替代者。仓库已有先例，照做即可：
   - `actorType` / `role` —— `kind` / `teamRole` 的 legacy alias，仍接受；
   - `audience` —— `roles` 的前身，legacy-read only，新写入一律发 `roles`；
   - `BootstrapConfig.webSso` —— 已挪到 `/v1/config/public`，但仍照发，因为
     已发布客户端只从 bootstrap 里读快捷登录目标，删掉会让它们登录不了。
3. **双读双写，删除单独做。** 新字段落地后，过渡期读路径同时认新旧（旧值缺失时
   回退），写路径两边都写。删除旧形状是一个独立动作，要有"确认无人使用"的证据
   （旧版本流量、发布记录），不能和新功能塞进同一个 PR 顺手删。

## 数据库同样走 expand-contract

- 迁移**只做加法**：加列、加表、加可空约束、加索引、加新函数。
- 删列、删表、改列类型、加 `NOT NULL`、改函数签名，必须拆成多步：
  **先加新的 → 双写 / 回填 → 确认无人读旧的 → 再删**。旧 daemon 的查询在中间
  任何一步都不能报错。
- 迁移必须可重入（`deploy/self-host/init/apply-migrations.sh` 会重跑），并且
  不能依赖"客户端已升级"才成立的前提。
- 变更仍按 `AGENTS.md` 的 Supabase 流程走 MCP，并同步留下 migration + pgTAP。

## 真的需要破坏性变更时

出口是**新端点或新版本路径**，不是改旧接口：旧路径并行保留，直到确认没有旧
daemon 在用，再单独论证删除。删除旧形状需要一次显式决定，而不是顺手清理。

## 为什么是 daemon

daemon 随 desktop 打包（`apps/daemon/Cargo.toml` 里的 amuxd sidecar），但服务端
没有任何可靠的通道强制旧 desktop 升级。直接改字段，等于把"服务端发一次版"变成
"所有未升级用户的同步链路同时故障"——而这类故障只会在用户机器上出现，服务端
日志里看不到。

## 考虑过的其它方案

**服务端拒绝旧版本、要求升级。** 没有可用的强制升级通道，效果是把旧客户端直接
踢下线；这比兼容它们的成本高得多。

**直接改字段，靠"大家都会升级"兜底。** 省事，但把兼容成本转嫁给了最不可能
被观测到的位置——用户本地。本仓库已经为此保留过三处 legacy 形状，说明这个成本
是真实发生过的。

**给每个端点都开版本号（`/v2`）。** 语义整体变化时是合适出口，但作为默认手段
会让实现和维护翻倍。默认仍是只增不改，版本路径留给真正整体重写的场景。
